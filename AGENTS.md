# Inventura — правила для Codex

Эти инструкции применимы к репозиторию `Inventura` и должны соблюдаться при любых изменениях кода.

## Структура проекта
- Не смешивать фронтенд и бэкенд: проект — чистая фронтенд PWA (статические страницы в корне). Все UI/логика в `js/` и стили в `assets/`.
- Не создавать новые верхнеуровневые папки без необходимости; добавляйте файлы в существующие директории.

## Контекст и стек
- Лёгкое PWA: HTML, Tailwind, Vanilla JS.
- Хранение: IndexedDB (локально), Supabase/Postgres для синхронизации.
- Предпочитать небольшие, безопасные изменения, не ломать существующие импорты/форматы данных.

## Данные и конфигурация
- Основной источник данных — локальные IndexedDB и синхронизация в Supabase.
- Конфигурация Supabase хранится в `config/supabase-config.js` (в репозитории может быть пример `*.example.js`). Никогда не коммитить реальные ключи — использовать `.env` или инструкции в README.
- При изменении форматов импорта/экспорта сохранять совместимость: не удалять поля без миграции.

## PWA и офлайн
- Сервис-воркеры (`sw.js`) и манифесты важны для работы офлайн — тестировать поведение в режимах offline/online.
- При изменении кеширования явно указывать обновления манифеста и поведение миграции кэша.

## Безопасность
- Никогда не коммитить секреты и ключи (`SERVICE_KEY`, `ANON_KEY`).
- Для внешних загрузок валидировать тип/размер и сохранять в `uploads/` или `assets/`, не доверять пользовательским путям.

## Автотесты и скрипты
- Добавлять тесты в `tests/` при изменении логики импорта/парсинга.
- Скрипты разработки и сборки должны оставаться простыми; обновлять инструкции в `README.md`.

## Прочее
- Малые изменения с низким риском можно вносить напрямую; изменения форматов данных или поведения синхронизации — через PR с описанием миграции.
